📋 Repository Status

V-PRO (Valencia Proactiva) es un proyecto candidato a la convocatoria AD.TR.15 — Premios para proyectos de datos abiertos y periodismo de datos del Ayuntamiento de València 2026, categoría Datos Abiertos. 🛑 Hallazgo crítico #1 — Stack drift total.
El canonical stack declarado en esta sesión (Vanilla PHP + SQLite + Vanilla JS + Cron) no coincide con el stack real del proyecto (Python + FastAPI + SQLAlchemy + GeoAlchemy2 + PostgreSQL/PostGIS + Celery + Redis + Docker Compose, frontend previsto en Next.js + Tailwind + MapLibre). El 100% del backend existente queda fuera del stack canónico. Requiere decisión explícita antes de ejecutar la Fase 4. Ver § Awaiting Decision.
🛑 Hallazgo crítico #2 — 4 bugs bloqueantes en Fase 1 del producto.
(1) Columna metadata vs extra_data desincronizada entre modelo, ingestor y query espacial. (2) Import inválido from shapely import geojson en Shapely 2.x. (3) Task Celery declarada async def (no soportado en Celery 5 sin wrapper). (4) Sin creación automática de tablas (no hay Base.metadata.create_all ni Alembic). Con estos bugs la ingesta no persiste datos. Detalle en § Proposed Tasks.
🛑 Hallazgo crítico #3 — Credenciales por defecto en Docker Compose.
docker-compose.yml contiene POSTGRES_PASSWORD: [credential redacted] hardcodeado y backend/.env replica la misma credencial. Aunque el archivo .env está en .gitignore, la misma contraseña aparece literal en el compose versionado. Rotar antes de cualquier deploy y mover a secrets server-side.

  2. ¿Se puede borrar backend/.env del working tree tras confirmar la rotación del password? (No se pierde nada porque .env.example cubre el template, pero suele contener tu credencial local de dev.)

  4. ¿Hay restricción presupuestaria sobre el VPS Hetzner inicial? El plan asume ~$4/mes (canonical); puedo dimensionar RAM en función de si mantenemos Postgres o migramos a SQLite.

# ADR-001 — Desviación del canonical stack: Python + PostGIS para V-PRO

**Status:** Accepted
**Date:** 2026-05-09
**Deciders:** Tech Lead + Product Owner

## Context
El proyecto V-PRO responde a la convocatoria AD.TR.15 (Ayuntamiento de València,
premio Datos Abiertos 2026). Su núcleo funcional es geoespacial: calcular zonas
de impacto urbano con buffers métricos, emparejar ubicaciones ciudadanas con
eventos activos mediante ST_DWithin, y reproyectar geometrías entre CRS.

El canonical stack declarado en el equipo es: Vanilla PHP + SQLite + Vanilla JS + Cron.

## Options considered
1. Migrar al canonical stack (SQLite + SpatiaLite + PHP).
2. Excepción documentada: mantener Python + PostGIS, retirar piezas accesorias.
3. Híbrido: API HTTP en PHP, pipeline batch en Python.

## Decision
Se adopta la opción 2:
- Backend HTTP: Python 3.11 + FastAPI + SQLAlchemy.
- DB: PostgreSQL 15 + PostGIS.
- Scheduler: **Cron** (Celery + Redis eliminados).
- Frontend: HTML + Vanilla JS + MapLibre (Next.js/Tailwind/Framer descartados).
- Infra restante (Nginx, Cloudflare Tunnel, Tailscale, Hetzner, unattended-upgrades, R2): canonical.

## Consequences
+ Velocidad: mantenemos el plazo de 1 mes del concurso.
+ Capacidad: PostGIS cubre todas las operaciones espaciales del diseño.
+ Superficie: eliminamos Celery, Redis, Tailwind, Framer, GeoPandas.
- Desviación del canonical en dos ejes (runtime backend, DB engine) — se revisa al cierre del MVP.
- Mayor coste de mantenimiento si el equipo es mayormente PHP.

## Revisitación
Se reevalúa esta decisión al cierre de Fase 3 (entrega del frontend).
